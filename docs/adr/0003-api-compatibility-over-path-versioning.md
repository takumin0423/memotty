# API のパスにバージョンを入れず、互換性のルールで守る

API は `/api/v1/*` ではなく `/api/*` の直下に置き、後方互換性のルールで古いクライアントを守る。Web アプリは API と同時にデプロイされるのでバージョンがずれないが、Chrome 拡張と Mac アプリは古いバージョンのまま新しい API を呼び続けることがある。主要なガイドラインはバージョンをパスに入れるかどうかで意見が分かれている（入れる：Google AIP-185、Microsoft Graph／入れない：Azure、Zalando）。一方で「同じバージョンの中では追加しかしない」「クライアントは知らないフィールドを無視する」という点はすべてのガイドラインで一致しているので、その共通部分を守ることにした。

## Considered Options

- **`/api/v1/*` にする**：将来 v2 を並べて動かすための保険になる。ただ、`/api/*` を「暗黙の v1」とみなせば、後から `/api/v2/*` を足すこともできるので、今プレフィックスを付ける必要はないと判断した。
- **Stripe のような日付ベースのバージョンをヘッダで指定する**：細かく制御できるが、古い形のレスポンスに変換する層が必要で 1 人で開発するには重い。Hono RPC の静的な型でも、バージョンごとに形が違うレスポンスを表現できない。

## Consequences

- 破壊的変更はしない。具体的には、フィールドやエンドポイントの削除、名前の変更、型やデフォルト値の変更、リクエストへの必須フィールドの追加はしない（Google AIP-180 に準拠）。追加は許可する。
- クライアントは、レスポンスに知らないフィールドがあっても壊れないように書く。
- Mac アプリを最初にリリースする前に、クライアントが自分のバージョンを送り、サーバーが古すぎるクライアントに「アップデートしてください」と返す仕組みを入れる。Tauri の updater にはそのための仕組みが無いので、自分で作る必要がある。
- `GET /api/health` はバージョンと関係なく、この位置に置き続ける。
